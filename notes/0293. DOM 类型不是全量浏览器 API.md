## 1. 现象：`SerialPort` / `navigator.serial` 报错

在 TypeScript 项目里直接写 Web Serial：

```ts
const port = await navigator.serial.requestPort({
  filters: [{ usbVendorId: 0x1001, usbProductId: 0x2002 }],
})
await port.open({ baudRate: 115200 })
```

即便 `tsconfig` 里已经开了 `"lib": ["ES2022", "DOM", "DOM.Iterable"]`，编辑器仍可能报：

- `Property 'serial' does not exist on type 'Navigator'`
- `Cannot find name 'SerialPort'`

浏览器里（Chrome / Edge，以及较新的 Firefox）运行时 API 是存在的，缺的是 **TypeScript 类型**，不是运行时实现。

## 2. `lib: ["DOM"]` 实际覆盖什么

`lib` 里的 `"DOM"` 对应 TypeScript 发行包自带的 `lib.dom.d.ts`（以及相关的 `lib.dom.iterable.d.ts` 等）。

它主要覆盖：

- 传统 BOM / DOM：`window`、`document`、`HTMLElement`、事件、`fetch`、`URL` 等
- 已进入多引擎共识、由官方 DOM lib 流水线生成的 Web API

它 **不是**「MDN 上能查到的每一个浏览器 API」的类型全集。

像 Web Serial、WebUSB、WebHID、Web Bluetooth 这类，默认 DOM lib 里往往找不到对应声明。

## 3. TypeScript-DOM-lib-generator 的收录规则（≥2 引擎）

内置 `lib.dom.d.ts` 由 [TypeScript-DOM-lib-generator][1] 生成，并同步发布为 [`@types/web`][2]。

仓库 README 写明收录门槛：

> A feature needs to be supported by two or more major browser engines to be included here … **Gecko** (Firefox)、**Blink** (Chrome/Edge)、**WebKit** (Safari)。

要点：

- 至少 **两个** 主流引擎实现，才进入默认 DOM 类型
- Chromium 系（Chrome / Edge / Opera 等）算 **同一个** Blink 引擎，不能凑成「两个引擎」
- 不满足门槛的 API，即便 Chrome 早就有了，也不会进 `lib.dom.d.ts`

## 4. Web Serial 为何不在默认 DOM 类型里

Web Serial（`navigator.serial`、`SerialPort` 等）长期只有 Blink 实现；WebKit 至今仍持反对/未实现态度。

时间线（便于理解「为何类型滞后」）：

| 阶段 | 引擎情况 | 对 DOM lib 的含义 |
| ---- | -------- | ----------------- |
| 早期～Firefox 150 | 基本只有 Blink | 不满足 ≥2 引擎，不会进默认 DOM lib |
| Firefox 151（2026）起 | Blink + Gecko | 引擎数达标；是否/何时合入 `lib.dom.d.ts` 仍取决于 DOM-lib-generator 流水线 |
| Safari / WebKit | 仍未支持 | 跨引擎共识仍不完整 |

因此在很长一段时间里（以及当前大量项目依赖的 TS 版本自带 DOM lib 里），`SerialPort` 等类型 **不会** 随 `"lib": ["DOM"]` 自动出现。

类型补齐路径仍然是 DefinitelyTyped 上的独立包，而不是指望内置 DOM lib「碰巧有」。

## 5. 正确补齐方式：`@types/w3c-web-serial` + 加载配置

### 5.1. 安装类型包

```bash
npm i -D @types/w3c-web-serial
```

包来自 DefinitelyTyped：[`@types/w3c-web-serial`][3]，为 [Web Serial 规范][4] 提供 `Serial`、`SerialPort`、`Navigator.serial` 等全局声明。

光安装还不够：还要让当前工程的 TypeScript 编译上下文 **加载** 这份声明。下面两种方式二选一即可。

### 5.2. 方式 A：`compilerOptions.types`

在对应的 `tsconfig`（例如 `tsconfig.app.json`）里显式列出：

```json
{
  "compilerOptions": {
    "lib": ["ES2022", "DOM", "DOM.Iterable"],
    "types": ["w3c-web-serial"]
  }
}
```

注意：一旦写了 `types`，TS **只会** 自动从 `@types` 里加载列出的包，其它 `@types/*` 不再默认全部纳入。还需要别的全局类型时，继续往数组里加，或改用下面的 triple-slash。

### 5.3. 方式 B：triple-slash `reference`

在会被编译纳入的环境声明文件里写：

```ts
/// <reference types="w3c-web-serial" />
```

这种方式不依赖 `compilerOptions.types` 白名单；也可以和 Vite 自带的 `/// <reference types="vite/client" />` 写在同一个 `.d.ts` 里。

### 5.4. 和手写 `declare global` 的区别

- 优先用官方/社区维护的 `@types/w3c-web-serial`
- 仅在包缺失、过时，或要收窄项目自有类型（例如自建 `SerialPortFilter`）时，再在工程内 `declare` / 自建类型

## 6. 和 Vite / `vite-env.d.ts` 的关系

Vite 脚手架通常在 `src/vite-env.d.ts` 里自带：

```ts
/// <reference types="vite/client" />
```

这只引入 Vite 客户端类型（`import.meta.env`、静态资源模块等），**不会**带上 Web Serial。

因此 Web Serial 可以：

- 写在 `tsconfig` 的 `"types": ["w3c-web-serial"]` 里（`vite/client` 仍用原来的 triple-slash）
- 或在同一个 `vite-env.d.ts` 里再加一行 `/// <reference types="w3c-web-serial" />`

两种都能消除 `navigator.serial` / `SerialPort` 的类型报错；选一种保持即可，不必两套都写。

## 7. 同类例子（WebUSB、WebHID、Bluetooth…）

同一类「浏览器里有（或部分引擎有）、默认 DOM lib 没有」的 API，常见也是走 DefinitelyTyped：

| API | 类型包 |
| --- | ------ |
| Web Serial | [`@types/w3c-web-serial`][3] |
| WebUSB | [`@types/w3c-web-usb`][5] |
| WebHID | [`@types/w3c-web-hid`][6] |
| Web Bluetooth | [`@types/web-bluetooth`][7] |

用法同类：`npm i -D …`，再用 `compilerOptions.types` 或 `/// <reference types="…" />` 加载。

## 8. 小结：DOM lib ≠ 浏览器 API 全集

- `"lib": ["DOM"]` = TypeScript 内置、由 DOM-lib-generator 按 **≥2 引擎共识** 生成的那一份，不是 MDN 全量
- Web Serial 等长期（或在当前 TS 自带 lib 中）不在其中，属于正常设计，不是配置写错
- 补齐路径：`@types/…` + `compilerOptions.types` 或 triple-slash（二选一）
- 看到 `Navigator` 上缺属性时：先查是不是「未进 DOM lib 的 Web API」，再决定装哪个 `@types` 包
